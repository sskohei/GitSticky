## 実装計画・判断記録（2026-11-04）

### メモのタグ（2026-11-07、ユーザー承認済み）

分類して探すために1メモへ複数タグを付ける。複数タグの絞り込みはANDとし、本文検索と併用する。mainから `feat/note-tags` を作成し、エディタの追加・解除・候補表示、カード表示、タグなし表示、ローカル保存とGitHub同期を実装する。既存メモを空のタグ配列として移行し、タグ付きファイルは旧版によるタグ消失を防ぐためschemaVersion 2にする。タグなしの既存形式は読み書きを継続する。SQLite移行・永続化・同期競合・UI操作を検証し、PRを作成する。

### 認証改善（2026-11-05、ユーザー承認済み）

標準認証をGitHub App Device Flowへ変更し、PATと起動ごとのパスフレーズ入力を除去する。公開Client ID / slugは開発者が設定する。App未登録のため実装・テスト・登録手順を先に完成させる。秘密鍵・Client Secretは配布しない。

Windowsはユーザー単位DPAPI、AndroidはKeystore AES-GCMで認証情報を保護する。RustにDevice Flowの間隔制限・期限切れ・キャンセル・トークン更新を集約し、更新は直列化する。Reactにはトークン/device_codeを返さない。認可済みリポジトリを一覧から選択し、切断してもメモを残す。以前のStronghold保管庫は削除せず、必要な場合だけOS保護領域へ移行する。認証/保存失敗/競合する更新/UIをテストし、Windows/Androidビルドを確認する。

以下の初期計画と原仕様にあるPAT・毎起動時の保管庫解除は、この承認済み認証方針で置き換える。

既存コードなし。以下を各Phaseの完了条件とする。

1. Tauri v2 / React / strict TypeScript / Tailwind / shadcn形式の共通UI、SQLiteマイグレーション、テーマがビルドできる。
2. メモCRUD、検索、ピン、色、CodeMirror、500ms保存、閉じる前の保存を実装しテストする。
3. RustのGitHubクライアント、Stronghold暗号化、接続確認、YAML形式を実装する。
4. 完全な一覧に基づく同期、SHA比較、競合コピー、CASによる追加入力保護、削除マーカーをテストする。
5. Androidプロジェクトを生成し、レスポンシブUI、復帰時同期とAPKビルドを確認する。
6. 型・Lint・Vitest・RustテストとWindowsインストーラのビルドを確認し、実施できなかった項目を明記する。

SQL Pluginにマイグレーションと接続プールを任せ、書き込みは同じプールを使うRustコマンドで行う。競合コピーの作成と元メモ更新は単一トランザクションで確定する。GitHub通信とPATの復号はRust側に限定する。Strongholdは毎起動時にパスフレーズで解除し、PATをReactへ返さない。ブラウザ単体では永続化や同期を模擬せず、Tauriでの起動を案内する。

確認した一次資料: [Tauri v2 SQL](https://v2.tauri.app/plugin/sql/)、[Stronghold](https://v2.tauri.app/plugin/stronghold/)、[前提条件](https://v2.tauri.app/start/prerequisites/)。検証結果は `testing.md` に記録する。

Windowsネイティブ環境でlibsodiumのUnix configureを直接実行できないため、Android向けは公式ソースをNDK/CMakeで構築する補助スクリプトを追加した。Windowsのシンボリックリンク権限がない場合は、TauriによるRustビルド完了後の共有ライブラリをコピーし、同じGradleプロジェクトでAPK化する。暗号処理の無効化やOSセキュリティ設定の変更は行わない。

Fine-grained PATの実際のContents書き込み権限を読み取りAPIだけで確実に確認する方法がないため、接続時はリポジトリ・ブランチ・返されるpush権限を確認し、書き込みの認可は最初の同期応答でも確認する。エラー時はdirtyと本文を保持する。接続テストのためだけに検証ファイルを作成・削除しない。

実装結果：Phase 1〜4の基盤・ローカル操作・接続・同期の実装と自動テストを追加した。Phase 5のAndroidプロジェクト・戻る操作・キーボード設定・APKビルドを追加し、Phase 6のドキュメント・型/Lint・テスト・Windowsインストーラ生成まで実施した。Vitest 25件、Rust 8件が成功。Windowsロック解除後には日本語入力・保存・プレビュー・検索・色・ピン・通常終了・再起動後の保持を実画面で検証し、チェックリスト表示と終了処理の不具合を修正した。実際のPATを使った端末間同期、Android実機・エミュレーター操作は未検証であり、全完成条件を実地で確認済みとは扱わない。

あなたは、Tauri v2、React、TypeScript、Rust、SQLite、GitHub REST APIに精通したシニアソフトウェアエンジニアです。

このリポジトリに、WindowsとAndroidで動作する「StickyNote」というクロスプラットフォームのメモアプリを実装してください。

設計ドキュメントだけではなく、実際に動作するアプリケーションを作成してください。

## 1. プロジェクト概要

StickyNoteは、ユーザー自身が用意したGitHubリポジトリにMarkdownファイルを保存し、WindowsとAndroidの間でメモを同期するアプリです。

メイン画面には色付きの付箋がグリッド状に並びます。付箋にはタイトルが表示され、クリック・タップするとMarkdownエディタが開きます。

### 最重要要件

- WindowsとAndroidに対応する

- 両OSで同じReactベースのUIを使用する

- 付箋一覧はレスポンシブなグリッドレイアウトとする

- 自由配置・ドラッグ配置は実装しない

- Markdown形式でメモを保存する

- オフラインでも作成・閲覧・編集できる

- GitHubのユーザー指定リポジトリと双方向同期できる

- GitHub以外にバックエンドサーバーを必要としない

- 通信エラーや編集競合でデータが失われないようにする

- デフォルトUI言語は日本語とする

## 5. GitHub保存形式

GitHub側ではメモをMarkdownファイルとして保存してください。

保存パス:

notes/{noteId}.md

ファイル名にはUUIDを使用します。

Markdownの先頭にはYAML Front Matterを配置します。

フィールド:

- schemaVersion: 1

- id

- title

- color

- pinned

- createdAt

- updatedAt

Front Matter以降をMarkdown本文とします。

作成時・更新時は正しいYAMLエスケープを使用してください。

パーサーは不正なデータを安全に扱い、読み取りに失敗したファイルを勝手に削除しないでください。

ファイルはUTF-8で保存してください。

同期によるダウンロードだけではupdatedAtを更新しないでください。

アプリが管理してよいGitHub上のファイルはnotes/配下の対応Markdownファイルだけです。

[README.md](http://README.md)やその他のファイルを勝手に変更・削除しないでください。

## 6. GitHub接続

MVPではFine-grained Personal Access Tokenを利用します。

ユーザーが以下を設定できるようにしてください。

- Personal Access Token

- owner

- repository

- branch

接続時にリポジトリの存在、対象ブランチ、必要なアクセス権限を確認してください。

トークンには、対象リポジトリのContents: Read and writeを使用するように案内してください。

GitHub REST APIを使い、Git CLIのインストールを必要としない構成としてください。

アクセストークンはStrongholdで暗号化して保存してください。MVPではユーザーが設定したアプリ用パスフレーズで保護します。

Strongholdの鍵をソースコードに埋め込んだり、固定のパスワードを使用したりしてはいけません。

可能な限りGitHubへの通信と秘密情報の取り扱いはRust側にまとめ、ReactへPATを返さない設計にしてください。

トークン、認証ヘッダー、本文をデバッグログに出力してはいけません。

アプリが未接続の場合でもローカルメモは使用可能にしてください。

新しい端末では同じリポジトリを設定することで同期できるようにしてください。PATは端末ごとに設定します。

## 7. 同期エンジン

双方向同期を実装してください。

GitHub APIとの通信処理は抽象化し、テスト時にはモックに差し替えられるようにしてください。

### 同期順序

1. 同期処理の多重実行を防止する

2. ローカルの未同期変更を取得する

3. GitHub上のファイル一覧とSHAを取得する

4. 必要なリモートファイルを取得する

5. ローカル・リモート・前回同期状態を比較する

6. 競合を検出する

7. リモート変更を安全にローカルへ反映する

8. ローカル変更をGitHubへアップロードする

9. 成功したファイルのSHAと同期状態を更新する

10. 同期結果をUIへ通知する

GitHubのディレクトリ一覧取得にはContents APIまたはGit Trees APIを利用してください。

Git Trees APIを使用する場合はtruncatedを必ず確認し、不完全な一覧を完全な一覧として扱わないでください。

notes/ディレクトリが存在しない場合は空のノート領域として扱えますが、認証失敗や通信失敗を空の一覧と誤認してはいけません。

初回同期では、GitHub側のノートとローカルのノートを安全に統合してください。

### アップロード

GitHub Contents APIを利用します。

- 新規ファイルはPUTで作成

- 既存ファイルは前回SHAを用いてPUT

- 削除時は確認済みSHAを利用

- 変更処理は直列実行

- 409などの競合時には再取得・再判定

同じメモを同期処理中に編集した場合、アップロード成功時点で最新のローカル変更まで同期済みにしないでください。

アップロード対象のlocal_revisionと現在のlocal_revisionを比較し、追加編集がある場合はdirtyを維持してください。

### 競合処理

以下のルールを実装します。

- ローカルのみ変更: アップロード

- リモートのみ変更: ダウンロード

- 両方が同一内容: 同期済みとする

- 両方に異なる変更: 競合として保存

- リモートで削除、ローカル未編集: 削除を反映

- リモートで削除、ローカル編集済み: ローカル編集を別メモとして保護

- ローカルで削除、リモート変更済み: 自動削除せず競合として通知

競合時に古いデータを上書きしてはいけません。

MVPでは自動3-way mergeを必須としません。

競合したローカル内容は新しいUUIDで別のメモとして保存し、タイトルに「（競合コピー）」を付与してください。

競合コピーは通常のローカルメモとして維持し、後続の同期対象にしてください。

競合を繰り返し検出して無限にコピーが増えることがないよう、同期状態を正しく更新してください。

GitHub側の競合版とローカル競合コピーの両方をユーザーが確認できるようにしてください。

### 削除

ローカル削除では即座にDBから完全削除せず、deleted_atを使った削除マーカーを残してください。

同期成功後に安全なクリーンアップを実施してください。

オフライン時の削除も未同期操作として保持してください。

### エラー処理

以下を区別してください。

- ネットワーク接続失敗

- 認証エラー

- 権限不足

- リポジトリ不存在

- ブランチ不存在

- APIレート制限

- 競合

- 不正なMarkdown

- リモートの予期しない削除

- データベースエラー

エラー発生時に未同期データを削除してはいけません。

GitHubのRetry-After、X-RateLimit-Resetなどを尊重してください。

タイムアウトと指数バックオフを実装し、無限リトライを防いでください。

### 自動同期

以下で同期します。

- アプリ起動時

- アプリがフォアグラウンドへ戻ったとき

- 編集完了後、約15秒操作がなかったとき

- ユーザーが同期ボタンを押したとき

同期処理は同時に1件だけ実行してください。

自動同期は設定画面から無効化できるようにします。

Androidでアプリが完全に終了している状態の常時バックグラウンド同期はMVP対象外です。

## 9. アーキテクチャ

フロントエンドは以下の責務に分離してください。

- components: 共通UI

- features/notes: 付箋管理

- features/editor: Markdown編集

- features/settings: 設定

- features/sync: 同期UIとオーケストレーション

- stores: Zustand

- db: ローカルデータ操作

- lib: 共通ユーティリティ

- types: 型定義

Rust側は以下に分割してください。

- commands: Tauriコマンド

- github: GitHub REST APIクライアント

- security: トークン管理

- sync: 必要に応じた同期処理

- errors: 型付きエラー

GitHub通信処理とUIコンポーネントを密結合させないでください。

ReactコンポーネントからGitHub APIを直接呼び出さないでください。

GitHub APIのレスポンスとローカルDBのデータ構造を明確に分離してください。

Tauriの権限設定は必要最小限としてください。

## 13. 開発時の制約

- TypeScriptのanyを安易に使用しない

- Strict Modeを有効にする

- 不要な外部サービスを追加しない

- SupabaseやFirebaseを導入しない

- GitHub API以外のクラウドAPIを前提にしない

- リアルタイム共同編集は実装しない

- 自由配置の付箋UIは実装しない

- 画像添付・タグ・フォルダ機能は後回し

- SQLiteとGitHub間の同期安全性を優先する

- 機密情報をGitにコミットしない

- トークンをログに出力しない

- 破壊的なデータ変更を黙って実行しない

- モックのみで完成扱いにしない

- ユーザーデータを含むコードやログを不用意に外部送信しない

## 14. 開発の進め方

まず既存リポジトリのファイル構成を確認してください。

既存コードがある場合は、破壊しないように調査してから実装してください。

その後、次の処理を行ってください。

1. 技術構成の妥当性を確認する

2. 実装計画をdocs/[development.md](http://development.md)にまとめる

3. 実装を開始する

4. 各Phaseごとにテストを追加する

5. 型チェック・Lint・テストを実行する

6. Windows向けビルドを確認する

7. Android向けのビルドを確認する

8. 完了した機能と未完了機能を報告する

ローカル環境にAndroid SDKなどがなく、Androidビルドを実行できない場合は、未検証であることを明記してください。

Windowsネイティブ環境でのビルドを基本とし、WSLとWindowsのAndroid SDKパスを混同しないようにしてください。

ビルドやテストが失敗した場合は可能な範囲で修正してください。

エラーを放置したまま成功したと報告してはいけません。

実装内容について大きな設計判断が必要な場合は、セキュリティ、データ保全、保守性、MVPの単純さの順に優先して判断してください。

ただし、重要な仕様変更は勝手に行わず、ドキュメントに変更理由を残してください。

## 15. 完成条件

次の操作ができることを完成条件とします。

1. WindowsでStickyNoteを起動できる

2. 付箋を作成できる

3. Markdownで編集できる

4. アプリを再起動してもメモが残る

5. GitHubリポジトリを接続できる

6. GitHubにMarkdownファイルが保存される

7. Androidから同じメモを取得できる

8. Androidで編集した内容をWindowsで取得できる

9. オフラインで編集できる

10. 同時編集で両端末の内容が失われない

11. 同期エラー時もローカルメモが保持される

12. 自動同期と手動同期が使える

この完成条件を満たす、利用可能なMVPを実装してください。

**まずPhase 1から着手し、最終的なMVPの完成まで進めてください。単なる仕様書やUIモックの作成で終了しないでください。**
